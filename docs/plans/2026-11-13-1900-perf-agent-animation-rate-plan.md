# Снижение частоты анимации кнопок агентов - Plan

## Goal Capsule

- **Objective:** приложение Stream Deck на Mac перестаёт подтормаживать при переключении фокуса, пока агенты работают.
- **Means:** анимация работающих и ждущих ввода кнопок агентов идёт 2 кадра в секунду вместо 5 (KTD1); невидимые ключи по-прежнему не обновляются (KTD2).
- **Authority:** явные решения пользователя > `AGENTS.md`, `CONTRIBUTING.md`, `docs/maintenance/performance/README.md` > этот план.
- **Execution profile:** локальные коммиты в `main`, по коммиту на пункт. Без push, релиза и кликов по экрану пользователя.
- **Stop conditions:** вернуть вопрос владельцу, если для снижения частоты пришлось бы менять задержку обновления задач или период опроса T3.
- **Finish and ship:** `ce-work` доводит работу до локальных коммитов, приёмки и живого замера без кликов.

## Product Contract

### Problem Frame

При пяти работающих агентах плагин каждые 200 мс отправляет в Stream Deck новое изображение для каждой анимированной кнопки. Это около 25 изображений в секунду и примерно 150 КБ/с. Живой замер: Stream Deck загружает процессор на 20–23% с плагином и примерно на 1% без него. Переключение фокуса в приложении заняло 7,5 / 0,7 / 5,7 с с плагином против 1,1 / 0,7 / 0,7 с без него. Владелец не может спокойно работать в приложении Stream Deck.

### Key Decisions

- **Анимация идёт 2 кадра в секунду.** Governs R1. (session-settled: user-approved — выбрано вместо полного отключения анимации: движение остаётся видимым)
- **Невидимые ключи не получают изображений.** Governs R2. (session-settled: user-approved)
- **Задержка обновления задач и опрос T3 не меняются.** Governs R3. (session-settled: user-directed)

### Requirements

- R1. Каждая анимированная кнопка агента получает не больше 2 новых изображений в секунду.
- R2. Ключ, который исчез с экрана (`willDisappear`), не получает анимационных изображений, пока снова не появится.
- R3. Смена статуса или задачи по-прежнему отображается сразу, без ожидания кадра анимации. Период опроса 1200 мс и опрос T3 не меняются.
- R4. Прирост подтверждён замерами до и после по `docs/maintenance/performance/README.md`, попытка записана в `docs/maintenance/performance/journal.md`.

### Scope Boundaries

- Отрисовка SVG, опрос источников, лимиты и кнопки лимитов не меняются.
- Стоимость опроса T3 (около 178 КБ/с) известна и в этот этап не входит.
- Физический Stream Deck владелец проверяет сам.

## Planning Contract

### Key Technical Decisions

- **KTD1. Таймер 500 мс, кадр сдвигается на 2.** `DeckController.scheduleAnimation` в `src/stream-deck/controller.ts` переходит с 200 на 500 мс, `animationFrame` растёт на 2 по модулю 12. Цикл бегунка становится 3 с вместо 2,4 с, и темп остаётся близким к прежнему. При сдвиге на 1 цикл растянулся бы до 6 с. `render.ts` не меняется: шесть различимых фаз из двенадцати.
- **KTD2. Видимость уже обеспечена.** `src/stream-deck/actions.ts` регистрирует кнопку агента в `onWillAppear` и снимает её в `onWillDisappear`, а `renderOnce` рисует только зарегистрированные. Stream Deck шлёт `willDisappear` при уходе со страницы или из папки. Код не меняется; добавляется регрессионный тест, которого сейчас нет.
- **KTD3. Мгновенные обновления не зависят от таймера.** Смена статуса идёт через `requestRender` и `requestProjection`, а не через таймер анимации, поэтому R3 сохраняется без отдельной работы. Тесты это подтверждают.

### Risks & Dependencies

- Живой замер требует поставить сборку в живой плагин (`dist` связан ссылкой). Перед сборкой сохраняются `logs/`, после установки они восстанавливаются, а плагин перезапускается через `npx streamdeck restart com.xonika9.codex-deck`.
- Число и состав работающих агентов меняются сами, поэтому живые числа шумят. Основное доказательство — синтетический подсчёт изображений. Живые числа дополняют его.

## Implementation Units

### U1. Частота анимации 2 кадра в секунду

- **Goal:** R1, R2, R3.
- **Files:** `src/stream-deck/controller.ts`, `test/controller.test.ts`.
- **Approach:** KTD1. Обновить тесты, которые продвигают таймер на 200 мс ради кадра анимации.
- **Test scenarios:**
  - через 500 мс работающая и ждущая ввода кнопки получают по одному новому кадру, а простаивающая — ни одного;
  - через 400 мс новых кадров нет;
  - за 10 с одна анимированная кнопка получает не больше 20 изображений;
  - после `unregisterAgent` анимированный ключ не получает новых изображений, хотя таймер продолжает идти;
  - смена статуса отображается без продвижения таймера анимации.
- **Verification:** `npm test`, `npm run check`, `npm run lint`.

### U2. Замер и запись в журнал

- **Goal:** R4.
- **Files:** `docs/maintenance/performance/journal.md`; измеритель хранится во временном каталоге и не коммитится.
- **Approach:**
  - **Синтетика.** Стенд по образцу заглушек из `test/controller.test.ts`: настоящий `DeckController`, пять анимированных кнопок, искусственные часы на 60 с. Считаются вызовы `setImage` и их байты: 3 исходных прогона, затем 5 чередующихся для каждой версии.
  - **Живой замер без кликов.** Скорость отправки данных в Stream Deck меряется через `nettop`, загрузка процессора Stream Deck — через `top`. Берутся окна по 60 с до и после установки. Указывается число работающих агентов.
  - **Журнал.** Записываются числа, порог, ограничения и то, что не проверено.
- **Verification:** `node --test test/release-docs.test.ts` не нужен, потому что README не меняется. Проверить ссылки в изменённом журнале.
